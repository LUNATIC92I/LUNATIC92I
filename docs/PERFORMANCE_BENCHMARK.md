# Performance Benchmark

This is the **only** document in this repository allowed to state a
supported events/minute or latency figure (spec §24). Every other doc
that touches capacity — architecture notes, the development plan, sizing
guidance — must point here rather than repeat a number, because numbers
drift and a single source of truth is the only way "supported throughput"
stays honest.

## Read this before quoting a number from this page

**The environment below is a single-node, resource-constrained sandbox
VM, not a production deployment.** API, all four pipeline workers,
PostgreSQL, Redis, and OpenSearch all ran as processes on one 4-vCPU/15GB
host with no containerization overhead, no network hop between
components, and no other tenants competing for the same CPU. A real
deployment (`docker-compose.yml` for a single node, or `kubernetes/` for
a cluster) adds container and network overhead in exchange for isolation,
horizontal scaling, and high availability — none of which this benchmark
exercises. Treat every figure here as **"the pipeline is not broken and
here is a lower bound on what one modest machine can do,"** not as a
capacity planning number for any specific deployment target. Re-run this
suite against the actual target environment before making a sizing
commitment.

## Environment

| | |
|---|---|
| Host | 4 vCPU, 15 GiB RAM, single node, no containers |
| PostgreSQL, Redis, OpenSearch | Same host, default single-node config, loopback network |
| Database | Dedicated `lunatic_perf` PostgreSQL database — never the dev/test database |
| API + workers | `uvicorn` and the four pipeline workers (`parser`, `indexer`, `detection`, `alert`) run directly, one process each |
| Data | 100% synthetic, generated by the load-test harness itself; **no production credentials or data were used anywhere in this benchmark** (each simulated user registers its own throwaway organization and admin account with a synthetic password) |
| Harness | [Locust](https://locust.io) 2.46 for throughput/read-latency (`perf/locustfile.py`); a standalone `httpx`-based script for end-to-end alert latency (`perf/measure_alert_latency.py`) |
| Detection rule under test | `AUTH-003` — "privileged account authenticated from a non-internal address" — a single-event streaming rule, chosen because it fires immediately on the triggering event rather than on a scheduled window, so the number measured is pipeline latency, not polling-interval artifact |

## Results

### End-to-end alert-generation latency

Wall-clock time from `POST /ingest/events` to the resulting alert being
visible via `GET /alerts` — covering the full
ingest → parse → normalize → detect → alert path. 20 trials, each a
uniquely-addressed event so no trial can be satisfied by another trial's
alert.

| Metric | Value |
|---|---|
| Trials | 20 (20 succeeded, 0 timed out) |
| Min | 0.076 s |
| p50 | 0.080 s |
| p95 | 0.083 s |
| Max | 0.083 s |
| Mean | 0.080 s |

Raw output: `perf/results/alert_latency.json`.

### Ingestion throughput and API read latency

Mixed load: 30 concurrent simulated users (22 ingesting, 8 reading —
`perf/locustfile.py`'s `IngestionUser`/`ApiReadUser` at their configured
3:1 weight), ramped over 5 users/second, sustained for 90 seconds against
the same single-node stack, immediately after the alert-latency run
above (so the pipeline was already warm, not cold-started).

| Endpoint | Requests | Failures | Median | p95 | p99 | Req/s |
|---|---|---|---|---|---|---|
| `POST /ingest/events` | 7,627 | 0 | 200 ms | 420 ms | 460 ms | 85.5 |
| `GET /alerts` | 397 | 0 | 160 ms | 330 ms | 370 ms | 4.5 |
| `GET /incidents` | 461 | 0 | 150 ms | 310 ms | 390 ms | 5.2 |
| `POST /hunting/search` | 320 | 0 | 200 ms | 340 ms | 430 ms | 3.6 |
| `GET /users/me` | 166 | 0 | 150 ms | 300 ms | 380 ms | 1.9 |
| **Aggregated (all endpoints)** | 9,093 | 0 | 190 ms | 380 ms | 830 ms | 101.9 |

Zero failed requests across all 9,093 requests in the run.

Sustained ingestion rate: **85.5 events/second ≈ 5,130 events/minute**
on this one modest, unshared, non-containerized node — the number the
whole environment caveat above exists to contextualize. This is a lower
bound, not a ceiling: it reflects Locust's own client-side request
pacing under `wait_time=between(0, 0.05)` and 22 concurrent ingestion
users on 4 vCPUs shared with the rest of the stack, not the point at
which the pipeline itself started failing or queuing unboundedly (no
run in this pass pushed load high enough to find that point).

`/auth/register-organization` and `POST /api-keys` are markedly slower
(medians of 2.5 s and 0.73 s) because they run bcrypt password hashing
and encryption-key derivation — deliberately expensive, one-time
per-user operations (spec-mandated), not something a real workload calls
at request-time volume. They are excluded from the "sustained rate"
figure above for that reason; their cost is real but amortizes to
nothing once a tenant is provisioned.

Raw output: `perf/results/mixed_load_stats.csv`,
`perf/results/mixed_load_stats_history.csv`.

## What this benchmark found

Before any numbers could be captured, this benchmark surfaced two real
defects — the actual point of running it, not a side effect:

1. **`RedisStreamsEventBus.subscribe()` crashed every worker on any idle
   period of 5+ seconds** (any quiet night or weekend in production).
   redis-py applies a default client-side socket read timeout of ~5
   seconds independent of the `BLOCK` argument passed to `XREADGROUP`,
   so a topic with nothing published to it for 5+ seconds raised an
   unhandled `redis.exceptions.TimeoutError`. Invisible to the existing
   851-test suite because no prior test ever let a `subscribe()` call
   sit genuinely idle. Fixed in `app/core/eventbus.py` by passing an
   explicit `socket_timeout` wider than the block window, with a
   permanent regression test
   (`test_subscribing_to_an_idle_topic_survives_past_the_servers_own_block_window`).
2. **A misconfigured benchmark run, not a product bug**, initially made
   every trial time out: the alert worker process had been started
   without the load-test environment sourced, so it was silently
   consuming from an entirely different Redis database and writing to a
   different PostgreSQL database than the rest of the pipeline. Once
   restarted with the correct configuration it drained its backlog
   immediately and every subsequent trial succeeded — recorded here
   because a benchmark script's own environment plumbing is exactly the
   kind of thing worth flagging when it produces a false "the pipeline
   is broken" signal.

## Reproducing this benchmark

```bash
# End-to-end alert latency
python perf/measure_alert_latency.py --trials 20 --host http://localhost:8000

# Ingestion throughput + API read latency
locust -f perf/locustfile.py --host http://localhost:8000 --headless \
  -u 30 -r 5 -t 90s --csv perf/results/mixed_load
```

Requires the full stack running: API, parser/indexer/detection/alert
workers, and PostgreSQL/Redis/OpenSearch, all pointed at a dedicated
database — never a shared dev/test/production one.

## CI

The load tests run on a schedule (`.github/workflows/perf.yml`), not on
every push — they take minutes, need a full stack, and their numbers are
meaningful trend data over time rather than a pass/fail gate for an
individual commit. Results are archived as workflow artifacts on each
scheduled run.
