# LUNATIC-IT SIEM — Technical Risk Register (Phase 0)

Each risk has an owner discipline, a likelihood/impact rating, and a
mitigation or an explicit "accepted, revisit at phase X" decision. This
register is revisited at the end of every phase.

| # | Risk | Likelihood | Impact | Mitigation / Decision |
|---|---|---|---|---|
| 1 | Redis Streams cannot sustain the "large production" throughput target (1M events/min) once fan-out to multiple consumer groups (parsing, detection, correlation) is added. | Medium | High | `EventBus` abstraction (ARCHITECTURE.md §7.1) isolates the app from this; Phase 18 load tests decide whether Kafka is required before claiming that tier is supported. Never promise the number without the benchmark (per spec §24). |
| 2 | OpenSearch cluster operational complexity (shard sizing, mapping explosion from heterogeneous logs, hot-warm-delete tuning) underestimated. | Medium | High | Strict, mostly-`dynamic:false` index templates (see `opensearch_indices.md`); dedicated SIEM Engineer discipline owns index lifecycle; load/soak tests before claiming a retention/volume SLA. |
| 3 | PostgreSQL Row-Level Security adds query planning overhead and is easy to get subtly wrong (e.g., forgetting to `SET app.current_tenant_id` on a connection reused from a pool). | Medium | Critical (cross-tenant leak) | Session variable set in a single, tested middleware/connection-acquisition hook; automated cross-tenant IDOR test suite gates CI (spec §20); RLS is a second layer, not the only one. |
| 4 | Correlation engine statefulness (in-flight windows) is lost on worker restart/deploy, causing missed multi-stage detections. | Medium | Medium | Correlation state persisted in Redis (with TTL matching the rule window) rather than in-process memory, so a restart resumes from durable state; covered by a dedicated recovery test in Phase 7. |
| 5 | Clock skew between log sources (or deliberately falsified source timestamps) breaks time-window correlation/detection and can be used for evasion. | Medium | Medium | Use `ingestion_timestamp` as an evasion-resistant backstop alongside `event.timestamp`; large skew is itself flagged (THREAT_MODEL.md §3.4). |
| 6 | Idempotency/deduplication at ingestion is harder than it looks (retries, multi-homed collectors, at-least-once delivery) — risk of duplicate events inflating counts/alerts. | Medium | Medium | Deterministic idempotency key (`sha256(tenant_id+source+raw_hash)`) checked at the Ingestion Gateway before publish; deduping is a Phase 3 acceptance criterion, tested explicitly. |
| 7 | Secrets management is "TBD" at Phase 0 — hardcoding is an easy mistake under time pressure across many collectors/connectors. | Low (with discipline) | Critical | Centralize on a secrets manager (e.g., environment-injected from Vault/cloud KMS — exact choice made in Phase 1 infra design) from the first commit; `.env`/secrets are git-ignored and scanned for in CI (Bandit/secret-scanning) from Phase 1. |
| 8 | RBAC permission matrix (10 roles × N resource/actions) is large and easy to leave incomplete, silently defaulting to over-permissive. | Medium | High | Deny-by-default `require_permission()` dependency; a route with no explicit permission mapping fails closed (403), not open; RBAC test matrix is a named Phase 2 acceptance criterion. |
| 9 | OCSF mapping fidelity: real-world logs rarely map cleanly to OCSF classes; incomplete mappings could silently drop meaningful fields into "raw only". | Medium | Medium | `raw_event` is always retained (spec requirement), so nothing is unrecoverable; normalization test fixtures per source type catch regressions; OCSF version pinned (1.1.0) to avoid a moving target. |
| 10 | MITRE ATT&CK reference data goes stale if hardcoded; STIX/ATT&CK content updates periodically. | Low | Medium | Import/update mechanism (spec §12) rather than hardcoding; `mitre_techniques.version`/`updated_at` tracked so staleness is visible on the coverage page. |
| 11 | UEBA cold start: with no historical baseline, early anomaly detection will have a high false-positive rate. | High (initially) | Medium | UEBA baselines require a minimum observation window before alerting is enabled per entity; anomalies always carry a confidence level and context, never fire alone (spec §17). |
| 12 | Destructive SOAR actions (isolate host, disable user) could be misused or mis-triggered, causing real operational damage in a customer's environment. | Low (with controls) | Critical | Architecturally unreachable without the approval state machine (`PENDING_APPROVAL → APPROVED → EXECUTED`, dual control); dry-run mandatory first; every transition audit-logged (ARCHITECTURE.md §7.5). |
| 13 | Syslog UDP collector is inherently spoofable/lossy, conflicting with "never silently lose an event". | Medium | Low–Medium | Documented as a known, accepted limitation of the protocol (THREAT_MODEL.md §5); network allow-listing; TLS syslog recommended for anything requiring guarantees. |
| 14 | Multi-region/HA claims (spec §25) are aspirational at Phase 0; PostgreSQL/OpenSearch/Redis HA each have different operational maturity curves. | Medium | Medium | HA is explicitly scoped to Phase 19, built on infrastructure abstractions established from Phase 1 (12-factor config, no local state in app tier) so HA is additive infra work, not a rewrite. |
| 15 | Test/documentation debt accumulating if phases are rushed past their own acceptance criteria (spec explicitly warns against this). | Medium | High (to project credibility) | The phase workflow (spec §42/43) is enforced as a hard gate in `docs/DEVELOPMENT_PLAN.md` — no phase is marked done without its tests, security review, and acceptance criteria met. |
| 16 | Detection rule YAML DSL trying to express both simple and complex (multi-condition, sequence-aware) logic could become an ad hoc, hard-to-validate mini-language. | Medium | Medium | Strict Pydantic schema validation of the rule DSL, rule dry-run/testing tool required before enabling any rule in production (spec §7), version history so a bad rule can be reverted. |
| 17 | Cost/performance tension: OpenSearch document-level security (DLS) and PostgreSQL RLS both add per-query overhead at scale. | Low–Medium | Medium | Measured explicitly in Phase 18 load tests as part of the standard query-latency benchmark, not assumed free. |
